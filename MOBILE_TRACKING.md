# Departure, return and mobile tracking

Prototype implemented: departure with employee name/reason/condition notes/required condition photo; return with employee name/notes/required condition photo; one active trip per unit; server timestamps; append-only correction notes, GPS points and condition photos. SQLite triggers prohibit update/delete of recorded trip events and points. Inventory reference photos remain separately editable. GPS samples show accuracy, device capture time and server receipt time. There is no automatic claim that GPS is active when a trip starts.

Browser GPS is explicitly started by the user after departure, captures foreground samples at most every 10 seconds, reports permission/upload failures, and stops on a successful return submitted on that phone. Closing, reloading or suspending the page interrupts capture. Return from another device rejects further point uploads. This is not reliable full-trip/background tracking. No locations are silently collected before the employee chooses location capture. No offline GPS queue or route map is implemented yet.

Required native app work: iOS/Android background-location permissions, visible tracking state, employee confirmation, departure-to-return lifecycle, encrypted offline sample queue, restart/resume support, deduplicated uploads, gaps/accuracy reporting, and actual locked-screen tests on physical devices. Tracking follows the employee's phone, which must remain with the vehicle. It must never be presented as guaranteed vehicle tracking.

Access requirement: everyone in the same dealership can view live trip/location history; original events/photos/locations cannot be edited/deleted by employees; corrections append author/time/text. The prototype currently has one inventory and manually entered employee names. It has not implemented verified employee identities, dealership membership, per-trip upload authorization, or reliable native tracking. These must be implemented before real employee location collection. Browser UI and database guards are not protection against a server/database administrator with filesystem access.

Hosting/login remains unfinished. Do not deploy the local email-gated mode publicly without its gate. Existing Railway deployment checklist still applies.

Profile identity update: trip events and corrections take employee display name, stable account ID and email from the authenticated server account; request-supplied values are overwritten. Employee inputs removed; legacy demo events labeled unverified. The local email-gated mode cannot supply individual account identity, so trip/correction/GPS writes are blocked in that mode. The current app-auth configuration still supports one account; employee enrollment and dealership membership are not implemented.

Sold units and retention: Mark as sold hides a unit from default active inventory; Sold/All filters and Restore preserve access. An active trip prevents sale marking. The server performs automatic cleanup on startup and hourly: after 30 full days since soldAt, trip events/corrections, GPS points, and condition photos are permanently removed; basic unit details and reference photo remain. Active/restored units are excluded. Employees cannot manually edit/delete history; a private server maintenance function performs retention deletion. Restoring after cleanup cannot recover removed history. SQLite secure-delete and compaction reclaim storage; separate backup retention must also be configured when hosted.
